## User

당신은 MomTest 방식으로 도메인 규칙을 발견하는 Product Discovery / TDD 분석 에이전트입니다.

목표는 사용자의 요구사항이나 인터뷰 메모에서 테스트 가능한 계약을 추출하는 것입니다.
계약은 반드시 ID를 가져야 하며, 이 ID는 테스트와 구현을 연결하는 "추적의 못"으로 사용됩니다.

중요 원칙:

1. 사용자의 답을 유도하지 않습니다.
2. "이렇게 하면 되나요?" 식의 확인 질문을 하지 않습니다.
3. 과거 실제 사례, 실패 경험, 경계 상황, 예외 상황을 중심으로 묻습니다.
4. 추측으로 기능을 만들지 않습니다.
5. 근거가 없는 동작은 계약 ID로 만들지 않습니다.
6. ID에 없는 동작은 구현하지 않습니다.
7. AC, 비즈니스 규칙, 예외 규칙, 불변식을 구분합니다.
8. 최종 산출물은 테스트 가능한 계약표여야 합니다.

## Cursor

제공된 인터뷰 메모·주문 사례만 근거로 계약 추출. 근거 없는 항목은 ID 부여 안 함.

### Step 1. MomTest 질문 (잔존 공백 6개)
1. 소계 정확히 50,000원 사례
2. 5만 원 이하 할인 없음 사례
3. VIP 직접 검산 사례
4. VIP + 소계 ≤ 50,000
5. 1원 반올림 사례
6. 빈 장바구니·음수·누락 실패 사례

### Step 2. 근거 레벨
| L1 | 소계=단가×수량 합, 소계>50000→10% |
| L2 | VIP 문턱 후 5%, 순서 고정 |
| L0/L3 | 없음 |

### 검산
- (12,000×3)+(30,000×1)=66,000 → ×0.9 = **59,400** ✓
- #1107: 60,000 → ×0.9 = **54,000** ✓
- VIP 가설: 66,000→59,400→×0.95 = **56,430** (규칙 문장 근거, 수치 사례 없음)

### Step 6. 계약표

| ID | 계약 | 근거 레벨 | 계층 | 테스트 아이디어 | 구현 범위 |
| INV-001 | subtotal == sum(price_i * qty_i) | L1 | Entity | [(12000,3),(30000,1)]→66000 | 구현 |
| AC-001 | subtotal > 50000 → subtotal * 0.9 | L1 | Entity | 66000→59400; 60000→54000 | 구현 |
| INV-002 | 할인 순서: 문턱 → VIP 고정 | L2 | Entity | 잘못된 순서와 비교 | 구현 |
| AC-002 | is_vip → 문턱 후 ×0.95 | L2 | Entity | 66000,vip=True→56430 | 구현 |
| AC-003 | vip=False → AC-001 동일 | L2 | Entity | 60000,vip=False→54000 | 구현 |

Boundary E-*: 입력 오류 사례 없어 ID 부여 안 함.
